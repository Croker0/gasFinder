# Выступление: бэкенд-разработчик

**Проект «Заправка рядом».** Тема №5 — поиск ближайшей заправки по геолокации.
**Регламент:** 4–7 минут. Блок «Вероятные вопросы и ответы» в регламент не входит.

---

## 0. Сразу главное: в MVP бэкенда нет

Начну с того, что снимет главный вопрос, и скажу это прямо: **в текущем MVP серверной части нет.** Данные об АЗС лежат внутри приложения — локальный справочник на **26 станций** в `GasStationRepository`, пользовательские заправки — JSON в `SharedPreferences`, настройки и избранное — там же. Из сети приложение получает только тайлы карты OpenStreetMap.

В критериях роль бэкенд-разработчика помечена как «если есть». У нас её нет — **и это проектное решение, а не пробел.** Вот три причины, по которым мы его приняли осознанно.

**Первая: у нас нет источника реальных данных.** Цены на топливо не отдаются бесплатно и без договора. Любой публичный API потребовал бы ключа, биллинга и юридических отношений с поставщиком. Сервер, который отдаёт выдуманные нами же цены, — это сервер ради сервера.

**Вторая: демонстрация должна быть неубиваемой.** На защите приложение обязано работать при любом интернете в аудитории. Локальные данные гарантируют, что демонстрация не зависит от чужого сервера, хостинга и квот.

**Третья: приоритет по времени.** Учебная цель проекта — клиентская часть: геолокация, карта, разрешения, жизненный цикл, хранение. Мы вложили время туда, а не в поднятие инфраструктуры.

При этом **архитектура к серверу готова**: источник данных изолирован в `GasStationRepository`, UI и ViewModel с ним напрямую не работают. Подключение сети — это замена реализации одного класса плюс слой кэша, без переписывания интерфейса.

Дальше — как я вижу серверную часть, если проект развивать. Это не «когда-нибудь», это проработанный план.

## 1. Стек и почему именно он

**Язык и фреймворк: Kotlin + Ktor.** Причина простая и сильная: команда уже пишет на Kotlin. Один язык на клиенте и сервере означает **общие модели данных** — DTO описываются один раз и переиспользуются через `kotlinx.serialization`. Ktor лёгкий, асинхронный, быстро стартует и не тянет за собой тяжесть Spring.

**База данных: PostgreSQL + PostGIS.** Это ключевое решение. Наш главный запрос — «дай ближайшие АЗС к точке». В обычной таблице это сортировка всего справочника по вычисленному на лету расстоянию. PostGIS даёт геотип и **индекс GiST**, который умеет KNN-поиск по оператору `<->`, то есть «ближайшие» считаются по индексу, а не перебором. Для нашей задачи это попадание в цель.

Дополнительно: **Redis** — для кэша ответов «станции рядом» и rate limiting. **Flyway** — версионированные миграции.

## 2. Модель данных

Сущности и связи:

| Таблица | Поля (главное) | Связи |
|---|---|---|
| `users` | `id` UUID, `email` citext UNIQUE, `password_hash`, `consent_152fz_at`, `created_at`, `deleted_at` | 1→N `favorites`, 1→N `stations` |
| `brands` | `id`, `name`, `color_hex` | 1→N `stations` |
| `stations` | `id`, `name`, `brand_id`, `address`, `location geography(Point,4326)`, `is_open_24`, `has_cafe`, `has_shop`, `has_car_wash`, `source`, `is_verified`, `created_by` | N→1 `brands`, 1→N `fuel_prices` |
| `fuel_prices` | `id`, `station_id`, `fuel_type` enum, `price numeric(6,2)`, `updated_at` | N→1 `stations` |
| `favorites` | `user_id`, `station_id`, `created_at` | составной PK |

**Почему цены отдельной таблицей.** Цена меняется каждый день, и нам нужна история: пользователю полезно видеть «цена обновлена 2 часа назад», а не «цена вообще». Текущая цена — последняя запись по `(station_id, fuel_type)`. Денормализуем в кэше, когда понадобится скорость.

**Индексы под конкретные запросы:**
- `GiST (stations.location)` — главный: ближайшие АЗС;
- `UNIQUE (users.email)` — вход и защита от дублей;
- `(fuel_prices.station_id, fuel_type, updated_at DESC)` — последняя цена без сканирования истории;
- `(favorites.user_id)` — список избранного;
- `(stations.is_verified, is_open_24)` — фильтры.

**Миграции** — только через Flyway, файлами `V1__init.sql`, `V2__add_prices.sql`. Схема в репозитории, накатывается автоматически при деплое. Ручных правок в продакшене нет.

Главный запрос выглядит так:

```sql
SELECT s.*, ST_Distance(s.location, :point) AS distance_m
FROM stations s
WHERE ST_DWithin(s.location, :point, :radius_m)
ORDER BY s.location <-> :point
LIMIT :limit;
```

## 3. API

Версионируем с первого дня: базовый путь `/api/v1`. Аутентификация — JWT.

| Метод и путь | Назначение |
|---|---|
| `POST /auth/register` | регистрация |
| `POST /auth/login` | вход, выдаёт access + refresh |
| `POST /auth/refresh` | обновление access-токена |
| `POST /auth/logout` | отзыв refresh-токена |
| `GET /stations?lat=&lon=&radius=&fuel=&open24=&limit=` | **главный**: АЗС рядом, отсортированы по расстоянию |
| `GET /stations/{id}` | карточка АЗС с ценами |
| `POST /stations` | добавить свою АЗС |
| `PATCH /stations/{id}` | изменить свою АЗС |
| `DELETE /stations/{id}` | удалить свою АЗС |
| `PUT /stations/{id}/prices` | обновить цены |
| `GET /me/favorites`, `PUT /me/favorites` | избранное, синхронизация между устройствами |
| `GET /me/settings`, `PUT /me/settings` | настройки пользователя |

**Формат ответа** — JSON. Пример `GET /stations?lat=56.8389&lon=60.6057&limit=2`:

```json
{
  "items": [
    { "id": "st_01H...", "name": "АЗС №1 «Роснефть»", "brand": "Роснефть",
      "address": "ул. Белинского, 152", "lat": 56.82513, "lon": 60.55203,
      "distanceM": 4820, "isOpen24": true,
      "prices": { "AI92": 52.31, "AI95": 57.07, "AI98": 68.78, "DT": 62.39 } }
  ],
  "total": 26
}
```

**Коды ошибок** — осмысленные, одного формата (RFC 7807): `201` создано, `400` ошибка валидации, `401` нет или истёк токен, `403` нет прав на чужой объект, `404` не найдено, `409` email уже занят, `429` превышен лимит запросов, `500` внутренняя ошибка. Тело ошибки всегда одинаковое:

```json
{ "type": "validation_error", "title": "Некорректный запрос",
  "errors": [ { "field": "lat", "message": "должна быть в диапазоне -90..90" } ] }
```

## 4. Безопасность и валидация

**Пароли** хранятся только хешированными: **Argon2id** с индивидуальной солью (если окружение не позволяет — bcrypt со cost 12). Открытый пароль не пишется ни в базу, ни в логи. Отдельно требование: **соль генерируется на каждый пароль**, а сравнение — только за постоянное время.

**Аутентификация: JWT.** Access-токен живёт 15 минут, refresh — 30 дней и хранится в `HttpOnly` cookie, чтобы его не достал JavaScript. В access-токене только `sub` и срок — никаких персональных данных.

**Защита от инъекций** обеспечивается тем, что мы **не собираем SQL строками**: только параметризованные запросы через Exposed или prepared statements JDBC. Конкатенация пользовательского ввода в SQL запрещена на уровне ревью.

**Валидация входа** — на границе, схемой: координаты в диапазонах −90..90 и −180..180, цены больше нуля и с двумя знаками, длина строк, допустимые значения `fuelType` из enum. Плюс **rate limiting** на логин и регистрацию, чтобы перебор паролей был невыгоден.

**152-ФЗ.** Обработка персональных данных — регулируемая тема, поэтому:
- при регистрации **явное согласие** на обработку ПД, с отметкой времени в `consent_152fz_at`;
- **минимизация**: собираем только email, без ФИО, телефона и адреса — нам они не нужны;
- **хранение на территории РФ**, уведомление РКН как оператора ПД;
- **право на удаление и выгрузку** — удаление мягкое (`deleted_at`), с последующей анонимизацией;
- **логи без персональных данных**, шифрование данных при хранении и HTTPS/TLS при передаче.

Это не «галочка»: без согласия и минимизации приложение с регистрацией просто нельзя легально запускать в России.

## 5. Развёртывание и мониторинг

**Где запуск:** VPS или облако в РФ, всё в Docker Compose: приложение, PostgreSQL с PostGIS, Redis, Nginx как TLS-терминатор и reverse proxy.

**Переменные окружения**, а не секреты в коде: `DATABASE_URL`, `REDIS_URL`, `JWT_SECRET`, `ARGON2_PEPPER`, `SENTRY_DSN`. Секреты — в секрет-хранилище или `.env`, который не попадает в репозиторий. Миграции Flyway накатываются при старте контейнера.

**Логи** — структурные, в stdout, собираются централизованно; без персональных данных.

**Базовые метрики:** `/health` для проверки живости, `/metrics` для Prometheus и Grafana, время ответа p95 (цель — до 200 мс на выдачу ближайших АЗС), доля ошибок 5xx, число запросов в секунду, попадание в кэш Redis, ошибки в Sentry.

## 6. Тесты

Покрываем три группы.

**Unit-тесты** — валидация входных данных, границы координат, расчёт расстояния на сервере, логика формирования цены. Быстрые, без базы.

**Интеграционные** — с настоящим PostgreSQL через **Testcontainers**: миграции накатываются на чистом контейнере, проверяем сам SQL, индексы и что KNN-запрос реально сортирует по расстоянию.

**Сценарии, которые обязаны быть покрыты:**
- успешная регистрация → `201`;
- повторный email → `409`;
- неверный пароль → `401`, без подсказки «такого пользователя нет»;
- истёкший или подделанный токен → `401`;
- координаты вне диапазона → `400` с указанием поля;
- запрос ближайших без параметров, с `radius` и с лимитом;
- редактирование **чужой** станции → `403`;
- удаление своей станции → `204`, повторное → `404`;
- превышение rate limit → `429`.

Пример проверки: запрос ближайших с координатами `56.8389 / 60.6057` и лимитом 2 обязан вернуть ровно две станции и в порядке возрастания `distanceM`.

## Вероятные вопросы и ответы

**1. Получается, серверной части нет вообще? Тогда что вы защищаете как бэкенд-разработчик?**
Я защищаю проектное решение и его обоснование. В MVP данные локальные — это осознанный выбор под учебные цели и отсутствие источника реальных цен. Роль бэкенд-разработчика я закрываю как проектировщик: выше показана готовая схема серверной части, и клиент к ней уже подготовлен архитектурно.

**2. Почему не Firebase, если нужен бэкенд «за вечер»?**
Firebase быстрее поднять, но он не даёт того, что нам нужно: геопоиска ближайших точек с индексом и хранения в РФ. Firestore не делает «дай ближайшие по расстоянию» так, как это делает PostGIS. Плюс требования по персональным данным — на Firebase их сложнее соблюсти.

**3. Зачем отдельная таблица цен, не проще ли поле в станции?**
Проще, но тогда теряется история. А история нужна: пользователь должен видеть, свежая ли цена, а мы — понимать, когда её обновляли. Одно поле не отвечает на вопрос «когда это стало 57 рублей».

**4. Как вы защититесь от подделки цен пользователями?**
Отметка `is_verified`: данные от обычных пользователей попадают в базу как непроверенные и не показываются как официальные, пока их не подтвердят. Редактировать чужую станцию нельзя — `403`. Жалобы и модерация в бэклоге.

**5. Почему Argon2id, а не SHA-256?**
Потому что SHA быстрый — а быстрый хеш удобен для перебора. Argon2id специально сделан медленным и требовательным к памяти, поэтому подбор становится экономически бессмысленным. Это стандарт для паролей.

**6. Как приложение перейдёт на сервер без переписывания?**
Заменой реализации `GasStationRepository` на сетевую плюс слой кэша. Интерфейс экранов и ViewModel не меняются — именно для этого мы разделили слои. Плюс локальный справочник останется как fallback для офлайна.
